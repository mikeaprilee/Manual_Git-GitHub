1. Qué son Git y GitHub

Git es un sistema de control de versiones. Guarda "fotografías" de los cambios de un proyecto para poder saber qué cambió, cuándo cambió y quién lo cambió. También permite volver atrás sin perder el trabajo.

GitHub es una plataforma web que aloja repositorios Git. Añade herramientas para compartir código, trabajar con ramas, revisar cambios, organizar tareas y publicar páginas.

Elemento Explicación sencilla
Repositorio Carpeta del proyecto junto con todo su historial de cambios.
Commit Punto guardado del historial. Es como una foto con un mensaje.
Rama (branch) Línea de trabajo separada para desarrollar sin romper la versión principal.
Repositorio remoto Copia del repositorio que está en GitHub u otro servidor.
Repositorio local Copia que tienes en tu ordenador.
Pull request (PR) Propuesta para integrar los cambios de una rama en otra.
Clonar Descargar un repositorio remoto al ordenador.
Push / Pull Enviar cambios al remoto / traer cambios del remoto.
Fork (Bifurcación) Copia de un repositorio ajeno en tu propia cuenta de GitHub para trabajar sin afectar al original.
Regla mental: Edita archivos → prepara cambios → crea un commit → sube el commit a GitHub.

2. Preparación inicial

2.1 Instalar Git

Descarga Git desde https://git-scm.com/downloads e instálalo con las opciones recomendadas. Después abre Git Bash, PowerShell o la terminal de VS Code y comprueba la instalación:

git --version

Si aparece una versión, Git está listo. Si no, cierra y vuelve a abrir la terminal o revisa la instalación.

2.2 Crear una cuenta de GitHub

Para crear tu cuenta, entra en GitHub y pulsa Sign up. Utiliza una dirección de correo electrónico a la que tengas acceso, porque GitHub te enviará un mensaje de verificación y necesitarás confirmar la cuenta para utilizar todas sus funciones. Cuando la cuenta esté creada, activa la autenticación en dos pasos (2FA), ya que añade una segunda comprobación además de la contraseña y protege tus repositorios si alguien consigue averiguarla. Por último, elige un nombre de usuario profesional y fácil de recordar, porque aparecerá en la dirección de tu perfil y formará parte de las URL de los repositorios que publiques.

2.3 Configurar tu identidad de Git

Antes de crear commits, Git necesita conocer el nombre y el correo que asociará a cada commit. Esta información se guarda como parte de la identidad del autor del commit, pero no representa una cuenta iniciada en GitHub ni concede permisos para subir código. Es decir, user.name y user.email sirven para identificar quién creó un commit, mientras que la autenticación de GitHub se utilizará más adelante cuando Git o GitHub CLI necesiten comunicarse con un repositorio remoto.

git config --global user.name "Tu Nombre" git config --global user.email "tu-correo@example.com" git config --global init.defaultBranch main

La opción --global aplica esta configuración a todos los repositorios del ordenador. Si necesitas utilizar una identidad diferente en un proyecto concreto, puedes ejecutar los mismos comandos dentro de ese repositorio sin --global. La configuración init.defaultBranch main indica que, cuando inicialices un repositorio nuevo con git init, la rama inicial se llamará main. La opción --global hace que esta preferencia se aplique a todos los repositorios del ordenador.

Para comprobar la configuración actual, puedes ejecutar:

git config --global --list
Importante: El correo configurado debe coincidir con una dirección verificada en GitHub si quieres que la plataforma asocie correctamente los commits con tu perfil. Si prefieres no mostrar tu correo personal, puedes utilizar la dirección noreply que GitHub proporciona en Settings → Emails.

2.4 Diferencias entre Git y GitHub CLI

Git y GitHub CLI se utilizan desde la misma terminal, pero resuelven problemas distintos. Git es el sistema de control de versiones que trabaja principalmente con los archivos y el historial del repositorio local. GitHub CLI es una herramienta de comunicación y administración de GitHub que utiliza la red para consultar o modificar recursos alojados en la plataforma. Puedes trabajar sin conexión en los archivos del proyecto y utilizar Git para crear commits, cambiar de rama o revisar el historial. En cambio, las operaciones de GitHub CLI que consultan o modifican repositorios, Issues, Pull Requests o Actions necesitan conexión con los servidores de GitHub.

GitHub CLI no sustituye a Git: se complementan. git commit, git branch y git merge trabajan con el historial del repositorio; gh pr, gh issue y gh run trabajan con los servicios de GitHub. Algunos comandos de gh, como gh repo clone, utilizan Git internamente para clonar el repositorio. Aun así, Git y GitHub CLI siguen siendo herramientas diferentes: Git gestiona el contenido y el historial, mientras que gh gestiona recursos y servicios de GitHub.

Tarea Herramienta principal Motivo
Ver cambios en los archivos git status El estado está en la carpeta local
Crear un commit git commit El commit pertenece al historial local
Crear o cambiar de rama git branch / git switch Las ramas forman parte del repositorio Git; git switch permite cambiar entre ellas.
Subir o descargar commits git push / git pull Pertenecen a Git y sincronizan commits entre el repositorio local y el remoto.
Crear un repositorio en GitHub gh repo create Permite crear un repositorio remoto vacío o publicarlo a partir de una carpeta local existente.
Crear una Issue gh issue create Las Issues pertenecen a GitHub
Crear una Pull Request gh pr create La revisión ocurre en GitHub
Consultar Actions gh run list / gh run watch Las ejecuciones están en GitHub
Abrir un repositorio en el navegador gh repo view --web Se accede a la interfaz web de GitHub

Algunas órdenes de gh pueden utilizar Git internamente. Por ejemplo, gh repo clone termina descargando una copia del repositorio mediante Git, y gh repo create --source=. puede crear el repositorio remoto y asociarlo a una carpeta local. Esto no significa que Git y GitHub CLI sean el mismo programa: Git gestiona el contenido y el historial, mientras que gh gestiona recursos y servicios de GitHub.

💡 Idea clave: GitHub CLI es una herramienta de comunicación con GitHub. No sustituye a Git, pero puede utilizarlo internamente para descargar o subir código.

Identidad, autenticación y permisos no son lo mismo

En este proceso aparecen tres conceptos diferentes. La identidad de Git (user.name y user.email) indica quién figura como autor de un commit. La autenticación demuestra ante GitHub qué cuenta está realizando una operación. Los permisos determinan qué puede hacer esa cuenta, por ejemplo leer un repositorio privado, subir una rama o crear una Pull Request. Configurar el nombre y el correo no inicia sesión, y haber iniciado sesión tampoco concede permisos superiores a los que tiene la cuenta.

2.5 Instalar y autenticar GitHub CLI

Instala GitHub CLI desde https://cli.github.com/ o mediante el gestor de paquetes de tu sistema. Después comprueba que está disponible:

gh --version

gh auth login inicia el proceso de autenticación de GitHub CLI. Durante el asistente se elige el servidor, normalmente GitHub.com, el protocolo que se utilizará para conectar con los repositorios y el método para autorizar la cuenta. La opción HTTPS suele ser sencilla para empezar porque GitHub CLI puede gestionar las credenciales mediante el sistema de almacenamiento seguro disponible. También es posible utilizar SSH si previamente se han configurado claves SSH en la cuenta de GitHub.

gh auth login

Si eliges HTTPS, GitHub CLI puede ofrecer configurar Git para que utilice las credenciales de GitHub CLI cuando ejecutes operaciones como git push o git pull. Si aceptas esa opción, gh y git podrán utilizar la misma autenticación para comunicarse con GitHub, aunque cada herramienta seguirá teniendo una función distinta. Si eliges SSH, Git utilizará una clave SSH en lugar de las credenciales HTTPS.

Comprueba la cuenta y el método de autenticación:

gh auth status git remote -v

gh auth status muestra la cuenta autenticada en GitHub CLI y el protocolo configurado. git remote -v muestra a qué dirección remota está conectado el repositorio local. Ambos comandos comprueban cosas diferentes: el primero revisa la sesión de gh y el segundo la conexión configurada para ese repositorio.

Importante: GitHub CLI guarda las credenciales usando el mecanismo seguro disponible en el sistema cuando es posible. No copies tokens en comandos, scripts compartidos ni capturas de pantalla. Si sospechas que una credencial se ha expuesto, revócala desde GitHub y vuelve a autenticarte.

2.6 Crear y conectar un repositorio desde la terminal

Una vez configuradas la identidad de Git y la autenticación de GitHub CLI, puedes crear un repositorio completo sin abrir el navegador. En este flujo, Git prepara el proyecto local y guarda su historial, mientras que GitHub CLI crea el repositorio remoto y lo conecta con la carpeta local. Cada herramienta interviene en una parte diferente del proceso.

El flujo práctico completo se muestra en la sección 4. Allí se prepara la carpeta con git init, se revisan y preparan los archivos, se crea el primer commit y se utiliza gh repo create para crear el repositorio remoto, configurar origin y subir los commits. Sus opciones principales son --source=., --remote=origin y --push.

Importante: Antes de ejecutar git add ., revisa que la carpeta contenga únicamente los archivos que quieres versionar. Si hay archivos generados, dependencias, configuraciones locales o credenciales, debes incluirlos previamente en .gitignore. Git no ignora automáticamente los archivos que no deberían publicarse.

💡Ejemplo de contenido para .gitignore:

node_modules/ .venv/ .env .env.* dist/ build/ .vscode/

El archivo .gitignore indica a Git qué archivos o carpetas debe ignorar. Esto evita que git status muestre como archivos sin seguimiento elementos que se generan automáticamente o que solo deben existir en el ordenador local. .gitignore no borra esos archivos ni impide que existan en la carpeta; simplemente evita que Git los proponga para añadirlos al historial. Si un archivo ya se añadió a un commit, incluirlo después en .gitignore no lo elimina del historial. En ese caso hay que dejar de seguirlo con Git y, si contenía información sensible, revocar también la credencial expuesta.

2.7 Crear una Pull Request desde la terminal

Después de crear commits y subir la rama con Git, puedes abrir la Pull Request con GitHub CLI:

git status git push -u origin feature/mi-tarea gh pr create --base main --head feature/mi-tarea --title "Añade formulario de contacto" --body "Explica los cambios y cómo probarlos"

--base indica la rama que recibirá los cambios y --head la rama que los contiene. Si omites opciones, gh pr create ofrece un asistente interactivo. Antes de crearla, revisa que la rama y el repositorio sean los correctos.

💡 Regla rápida: usa git para trabajar con archivos, commits y ramas; usa gh para comunicar esos cambios a GitHub y gestionar la colaboración alrededor del código.

2.8 Desconectar o cambiar de cuenta

gh auth logout gh auth login

Usa gh auth logout si compartes el ordenador o necesitas cerrar la sesión actual. Si trabajas con varias cuentas, revisa siempre el resultado de gh auth status antes de crear repositorios, Issues o Pull Requests.

3. Conceptos básicos

Un repositorio tiene tres zonas locales principales más el servidor remoto en GitHub:

Working TreeEditas archivos
git add➔
Staging AreaPreparas cambios
git commit➔
Repo LocalHistorial guardado
git push➔
GitHubRepo Remoto
Zona Qué contiene Comando habitual
Working tree Los archivos que estás editando actualmente. git status
Staging area Cambios seleccionados para el próximo commit. git add
Repositorio local Commits guardados en el historial de tu equipo. git commit

Los archivos Untracked son archivos que existen en la carpeta del proyecto, pero que Git todavía no sigue. Para incluir uno de ellos en el próximo commit, utiliza git add archivo. Si no debe formar parte del repositorio, añádelo a .gitignore o elimínalo de la carpeta. Los archivos Modified, en cambio, ya forman parte del historial de Git y han cambiado desde el último commit. Puedes preparar sus cambios con git add archivo o descartarlos con git restore archivo, teniendo en cuenta que esta última opción elimina los cambios locales no guardados.

La Staging Area es una zona intermedia donde seleccionas qué cambios formarán parte del próximo commit. Si has añadido un archivo por error, git restore --staged archivo lo saca de esta zona, pero conserva sus modificaciones en el Working Tree.

Cuando ejecutas git commit, los cambios preparados dejan de estar pendientes y pasan a formar parte del historial local. En ese momento están guardados en el repositorio de tu ordenador, pero todavía no están disponibles en GitHub hasta que ejecutes git push.

3.1 Qué ocurre al ejecutar git init

Cuando ejecutas git init, Git crea una carpeta oculta llamada .git dentro del directorio actual. Esa carpeta contiene la información necesaria para controlar las versiones, pero todavía no incluye los archivos del proyecto. Al ejecutar git status, Git compara el contenido de la carpeta con el repositorio y muestra como Untracked files aquellos archivos que todavía no están siendo seguidos.

Por eso es importante ejecutar git init dentro de la carpeta concreta del proyecto. Si lo ejecutas por error en una carpeta superior, como tu carpeta de usuario, el Escritorio o Documentos, Git puede detectar como posibles archivos del proyecto otros documentos y carpetas personales que se encuentren dentro de ella.

3.2 Cómo leer git status

git status

Este comando es tu principal herramienta de orientación. Indica la rama actual, cambios modificados, archivos nuevos y si tu rama está por delante o por detrás de GitHub. Acostúmbrate a ejecutarlo antes y después de cada operación importante.

Cómo interpretar el resultado: Changes not staged for commit son cambios que aún no has preparado; Changes to be committed ya están en staging; y Untracked files son archivos nuevos que Git todavía no sigue. Si la salida dice working tree clean, no hay cambios locales pendientes.

4. Primer proyecto paso a paso

Opción A: empezar desde una carpeta local

Si el proyecto ya existe en una carpeta de tu ordenador, sitúate primero en esa carpeta e inicializa el repositorio local. Antes de preparar los archivos, crea o revisa el archivo .gitignore para indicar qué elementos locales no deben formar parte del repositorio.

cd ruta/de/tu/proyecto git init git status git add . git status git commit -m "Primer commit"

El primer git status permite revisar los archivos que Git detecta antes de prepararlos. Después de git add ., el segundo muestra qué archivos han pasado a la Staging Area y, por tanto, se incluirán en el commit. Si todo es correcto, git commit guarda la primera versión en el repositorio local.

Cuando el commit local esté preparado, puedes crear el repositorio remoto y conectarlo con la carpeta actual mediante GitHub CLI:

gh repo create mi-proyecto --public --source=. --remote=origin --push

gh repo create crea el repositorio en GitHub sin abrir el navegador. --public lo hace público; puedes sustituirlo por --private si no quieres que el código sea visible. --source=. indica que la carpeta actual es el origen, --remote=origin configura la conexión con el repositorio remoto y --push sube los commits existentes a GitHub. La creación del repositorio la realiza GitHub CLI, pero el historial y los commits siguen siendo gestionados por Git.

Opción B: descargar un repositorio existente

git clone https://github.com/USUARIO/REPOSITORIO.git cd REPOSITORIO

git clone descarga una copia del repositorio mediante su URL. Con GitHub CLI también puedes utilizar gh repo clone USUARIO/REPOSITORIO, que identifica el repositorio mediante su propietario y nombre y utiliza la autenticación de GitHub CLI para conectarse. Ambos comandos descargan los archivos y el historial necesario para trabajar localmente. Tras clonar el proyecto, entra en la carpeta con cd antes de ejecutar otros comandos de Git.

4.1 Flujo diario recomendado

El trabajo diario consiste en partir de una versión actualizada del proyecto, desarrollar una tarea aislada y revisar los cambios antes de compartirlos. La rama main se mantiene como referencia estable; por eso conviene actualizarla primero y crear después una rama propia para la funcionalidad, corrección o documentación que vayas a realizar.

  1. Vuelve a la rama principal y trae los cambios recientes: git switch main y git pull --rebase origin main
  2. Crea una rama para tu tarea: git switch -c nombre-de-la-tarea
  3. Edita y guarda tus archivos.
  4. Revisa lo que has cambiado: git diff y git status
  5. Prepara solo los archivos correctos: git add archivo o git add .
  6. Crea un commit pequeño: git commit -m "Añade formulario de contacto"
  7. Sube la rama: git push -u origin nombre-de-la-tarea
  8. Abre una Pull Request desde GitHub o desde la terminal con gh pr create.

La revisión con git diff y git status permite detectar cambios inesperados antes de preparar los archivos. Después, el commit debe reunir una modificación coherente y la rama se comparte con git push para que pueda revisarse mediante una Pull Request.

💡 Consejo: Haz commits pequeños. Un commit debería representar un cambio coherente, no una mezcla de diez tareas.

Ejecuta antes git clean -nd para revisar qué se borraría.

5.1 Cómo usar los comandos sin perderse

Un comando suele componerse de un programa (git), una acción (status, commit o push) y opciones o argumentos. Las opciones empiezan normalmente por - o --; los argumentos indican sobre qué archivo, rama o remoto actuar.

git add src/app.js git commit -m "Corrige la validación del formulario" git push -u origin feature/formulario
  • git add src/app.js selecciona solo ese archivo para el próximo commit; no guarda todavía el cambio en el historial.
  • git commit -m "..." crea el punto del historial con los cambios que ya estaban preparados.
  • git push -u origin feature/formulario sube la rama al remoto llamado origin. La opción -u recuerda la relación para que en los siguientes envíos baste con git push.

5.2 Verificar antes de confirmar o compartir

git status git diff git diff --staged git log --oneline -5

La secuencia responde a cuatro preguntas: ¿en qué rama estoy y qué archivos han cambiado?, ¿qué cambios aún no he preparado?, ¿qué entrará en el próximo commit? y ¿cuáles son mis últimos cinco commits? Si algo no coincide con lo esperado, detente antes de ejecutar commit o push.

Nota sobre git pull: equivale, de forma simplificada, a traer información del remoto y después integrarla. git pull --rebase suele mantener un historial más lineal, pero no es una solución automática para conflictos: si aparecen, debes resolverlos y continuar o abortar la operación.

6. Ramas y trabajo en equipo

La rama main (o master en proyectos antiguos) debe mantenerse estable. Cada nueva funcionalidad, corrección o experimento debería hacerse en una rama propia.

Una rama es una referencia independiente dentro del historial de Git que permite desarrollar una línea de trabajo sin modificar directamente la versión estable. No es una copia completa e independiente de todos los archivos: representa una línea de commits desde la que puedes avanzar y cuyos cambios después puedes integrar mediante una Pull Request, un merge o un rebase.

git switch main git pull --rebase origin main git switch -c feature/nombre-corto
Prefijo Uso Ejemplo
feature/ Nueva funcionalidad feature/pagina-contacto
fix/ Corrección de error fix/calculo-precio
docs/ Documentación docs/actualiza-readme
refactor/ Mejora interna sin cambiar el resultado refactor/ordena-servicios

6.1 Mantener una rama actualizada

git switch main git pull --rebase origin main git switch mi-rama git rebase main

Si todavía estás empezando, puedes sustituir el rebase por git merge main. El rebase deja un historial más lineal, pero requiere más cuidado si la rama ya se comparte con otras personas, porque modifica los identificadores de sus commits. Como regla práctica, utiliza rebase para actualizar una rama privada que solo utilizas tú. Si la rama ya se ha compartido y otras personas trabajan sobre ella, merge suele ser más seguro porque no reescribe su historial.

6.2 Compartir una rama

git push -u origin mi-rama

7. GitHub desde la web

7.1 Crear un repositorio

Al crear un repositorio desde la web, GitHub puede inicializarlo con archivos básicos como README.md, .gitignore o LICENSE. Si el proyecto todavía no existe en tu ordenador, estas opciones ayudan a preparar el repositorio desde el principio. Si ya tienes una carpeta local con git init y commits, es preferible crear el repositorio remoto vacío y subir después tu historial local. Si inicializas ambos lados con commits distintos, tendrás que integrarlos antes de poder sincronizarlos con normalidad.

  1. Pulsa el signo + de la esquina superior derecha y elige New repository.
  2. Escribe un nombre corto. Añade una descripción y decide si será público o privado.
  3. Marca Add a README si el repositorio empieza vacío.
  4. Añade .gitignore según el lenguaje (por ejemplo, Python, Node o Visual Studio).
  5. Pulsa Create repository.

Pestaña / sección Uso principal

7.3 Editar archivos desde GitHub

Abre un archivo y pulsa el icono del lápiz. Haz el cambio, escribe un mensaje y elige si quieres crear una rama nueva y una Pull Request. Para archivos nuevos usa Add file → Create new file. Para subir archivos usa Add file → Upload files.

💡 Cuándo usarlo: La edición web es útil para cambios pequeños, corregir el README y documentación. Para cambios grandes, clona el proyecto y trabaja localmente en tu editor de código.

7.4 Settings importantes

La sección Settings reúne las opciones de administración del repositorio. En Collaborators se gestionan las personas que pueden acceder al proyecto y sus permisos. En Branches puedes proteger ramas como main y exigir Pull Requests, revisiones o comprobaciones automáticas antes de fusionar cambios. Esta protección no impide modificar el repositorio: obliga a que los cambios sigan las reglas configuradas.

En Actions puedes revisar los flujos automáticos y sus resultados. En Secrets and variables se guardan credenciales que utilizarán los flujos sin escribirlas en el código. Finalmente, Pages permite publicar un sitio web estático a partir de una rama o de un flujo de Actions.

8. Pull requests y revisión de código

Una Pull Request (PR) es una conversación sobre un cambio antes de incorporarlo a otra rama. No es solo un botón de "fusionar": permite revisar, comentar, probar y documentar la decisión.

8.1 Crear una PR de calidad

Una PR de calidad facilita que otra persona entienda el cambio sin tener que reconstruir todo el contexto. El título y la descripción deben dejar claro el objetivo, la forma de probarlo y, si es necesario, el resultado visual. Si la PR resuelve una Issue, puedes utilizar palabras clave como Closes #12 para que GitHub la cierre automáticamente al fusionarla.

  1. Sube tu rama a GitHub.
  2. Pulsa Compare & pull request o abre la pestaña Pull requests → New pull request.
  3. Elige la rama destino, normalmente main, y tu rama de cambios.
  4. Escribe un título claro y una descripción con: qué cambia, por qué, cómo probarlo y capturas si afecta a la interfaz.
  5. Asigna revisores y enlaza la Issue correspondiente, por ejemplo: Closes #12.
  6. Revisa los checks automáticos y responde a los comentarios.

8.2 Revisar una PR

Para revisar una Pull Request, comienza leyendo su título y descripción para entender el objetivo. Después analiza cada modificación en Files changed, comprobando el contexto, los archivos incluidos, las pruebas y los posibles riesgos. En una línea concreta puedes dejar un comentario, hacer una sugerencia de código o iniciar una conversación; revisar no consiste únicamente en comprobar si el resultado final parece correcto.

  • Files changed: inspecciona cada cambio, no solo el resultado final.
  • Conversation: lee el contexto y las decisiones anteriores.
  • Commits: comprueba que los commits son comprensibles.
  • Review changes: comenta una línea, sugiere una modificación o aprueba.
Regla de etiqueta: Los comentarios deben ser concretos y respetuosos. Distingue siempre entre un error que bloquea la integración (debe corregirse) y una simple sugerencia de estilo.

Al terminar la revisión, puedes elegir entre tres estados. Comment deja observaciones o preguntas sin aprobar ni bloquear por sí solo. Approve indica que los cambios cumplen los criterios de revisión. Request changes solicita modificaciones antes de fusionar la PR. El efecto de estos estados depende de los permisos del revisor y de las reglas de protección configuradas en el repositorio.

8.3 Fusionar una PR

Cuando las revisiones y comprobaciones sean correctas, GitHub ofrece varias formas de integrar la PR. Merge pull request conserva los commits de la rama y añade un commit de fusión en la rama de destino. Mantiene el contexto de que dos líneas de trabajo se integraron, aunque puede hacer el historial más voluminoso.

Squash and merge combina los commits de la Pull Request en un único commit antes de incorporarlo a main. Es útil cuando la rama contiene commits intermedios, correcciones o mensajes que no aportan valor al historial principal.

Rebase and merge recoloca los commits de la Pull Request sobre la versión actual de main y los incorpora sin crear un commit de fusión. El resultado suele ser lineal, pero modifica los identificadores de los commits y requiere que la rama pueda aplicarse sin conflictos.

9. Conflictos y cómo resolverlos

Git puede combinar automáticamente los cambios cuando afectan a archivos o líneas diferentes. Aparece un conflicto cuando dos ramas modifican la misma zona de un archivo, cuando una rama modifica un archivo que la otra ha eliminado o cuando Git no puede determinar de forma segura qué resultado debe conservar. Git marcará el archivo para que decidas cómo integrarlo:

<<<<<<< HEAD contenido de tu rama ======= contenido de la otra rama >>>>>>> otra-rama

Una Pull Request puede mostrar el aviso This branch has conflicts that must be resolved cuando GitHub no puede combinar automáticamente la rama con su destino. Lo más recomendable es actualizar la rama y resolver el conflicto localmente, donde puedes revisar los archivos, ejecutar las pruebas y comprobar el resultado antes de subir la solución.

9.1 Pasos para resolver un conflicto

  1. Ejecuta git status para ver los archivos en conflicto.
  2. Abre cada archivo y decide qué contenido debe quedar.
  3. Elimina las marcas <<<<<<<, ======= y >>>>>>>.
  4. Guarda el archivo y revisa el resultado con git diff.
  5. Marca el conflicto como resuelto: git add archivo.
  6. Completa la operación: git commit si era un merge, o git rebase --continue si era un rebase.
  7. Ejecuta las pruebas antes de subir los cambios.

Los editores como VS Code pueden detectar las marcas y ofrecer opciones como Accept Current Change, Accept Incoming Change y Accept Both Changes. Estas opciones ayudan a eliminar las marcas, pero no sustituyen la revisión manual: después de utilizarlas debes comprobar que el código mantiene el comportamiento esperado y ejecutar las pruebas.

git status git diff git add archivo-en-conflicto git commit -m "Resuelve conflicto en archivo"
Cancelar: Si te has metido en un merge o rebase y no sabes continuar, puedes abortar con: git merge --abort o git rebase --abort. Esto no borra el trabajo anterior a esa operación.

10. Publicar un proyecto y GitHub Pages

GitHub Pages publica sitios estáticos: HTML, CSS, JavaScript y generadores compatibles. No ejecuta un servidor backend tradicional.

10.1 Desde la configuración web

  1. Ve a Settings → Pages en tu repositorio.
  2. En Build and deployment, elige Deploy from a branch.
  3. Selecciona la rama, normalmente main, y la carpeta / (root) o /docs.
  4. Pulsa Save y espera a que termine el despliegue.
  5. GitHub mostrará la URL pública del sitio en esa misma pantalla.

10.2 Con GitHub CLI

Crear un repositorio con gh repo create y publicarlo con GitHub Pages son operaciones diferentes. GitHub CLI puede ayudarte a consultar el repositorio desde la terminal con gh repo view --web, pero la publicación del sitio se configura en Settings → Pages o mediante un flujo de GitHub Actions, como se explica en el apartado anterior.

11. Buenas prácticas y seguridad

No subas contraseñas, tokens, claves privadas, certificados, archivos .env ni datos personales al repositorio. El archivo .gitignore ayuda a evitar que se añadan por accidente, pero debe configurarse antes del primer git add. Si un secreto llega a publicarse, no basta con borrar el archivo en un commit posterior: el valor puede seguir presente en el historial. Revoca o cambia la credencial inmediatamente y revisa el historial para retirar el archivo si fuera necesario. También conviene activar 2FA en GitHub y utilizar contraseñas únicas.

Un flujo de trabajo seguro utiliza ramas descriptivas, commits pequeños y comprobaciones locales antes de subir los cambios. Las ramas feature/, fix/ y docs/ permiten separar tareas y facilitan la revisión. En proyectos de equipo, la rama main debería estar protegida para impedir cambios directos y exigir una Pull Request con revisiones o pruebas automáticas antes de fusionar.

El archivo README.md debe explicar cómo instalar, ejecutar y utilizar el proyecto, además de indicar su estructura y requisitos principales. Las dependencias también necesitan mantenimiento: conviene revisar las actualizaciones y los avisos de seguridad que GitHub muestre. Dependabot puede detectar dependencias vulnerables o desactualizadas según la configuración del repositorio y proponer actualizaciones mediante Pull Requests.

11.1 Ejemplo de .gitignore

# Dependencias node_modules/ .venv/ # Secretos y config local .env .env.* # Archivos del sistema .DS_Store .vscode/ # Construcciones dist/ build/

11.2 Licencias

Una licencia indica qué pueden hacer otras personas con tu código. MIT es muy sencilla y permisiva; GPL exige mantener ciertas libertades si alguien redistribuye el código.

Elige la licencia conscientemente y añade un archivo LICENSE desde la creación del repositorio.

12. Errores frecuentes

Mensaje / situación Qué hacer
nothing to commit No hay cambios nuevos o ya están guardados. Ejecuta git status.
Muchos archivos Untracked Comprueba que ejecutaste git init en la carpeta correcta y revisa .gitignore. Antes de borrar archivos sin seguimiento, utiliza git clean -nd para previsualizar el resultado.
Please tell me who you are Configura tu user.name y user.email (Sección 2.3).
rejected / non-fast-forward Comprueba que estás en la rama correcta y que no tienes cambios locales pendientes. Después trae los cambios con git pull --rebase origin rama y vuelve a hacer push. Si tienes trabajo sin guardar, haz un commit o utiliza git stash antes de integrar.
remote origin already exists Comprueba con git remote -v o cambia la URL con git remote set-url origin URL.
Permission denied Revisa la cuenta autenticada, permisos del repositorio y la URL remota.
merge conflict Resuelve las marcas del archivo, haz git add y completa el merge o rebase.
Subí un secreto por error Revoca el secreto en el proveedor inmediatamente, cambia la credencial y revisa el historial; no basta con borrarlo en el último commit.

12.1 Deshacer cambios con seguridad

git restore archivo # descarta cambios locales no guardados git restore --staged archivo # saca un archivo del staging (un-add) git revert ID_DEL_COMMIT # crea un commit nuevo que deshace otro

Para deshacer un commit que ya está compartido en GitHub, es mucho más seguro usar git revert (que avanza el historial) que intentar reescribirlo con un reset destructivo.
